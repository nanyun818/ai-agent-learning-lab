Langfuse不是一个天然知道正确答案的裁判。人、代码、模型都能产生分数，平台负责记录、关联和分析，也可以编排模型评分。promptfoo和DeepEval也同时支持代码规则与模型评分。不能用“人工还是Langfuse”作二选一：人工是一种判断方式，Langfuse是一种工作工具。

工程上合理的组合是：人定义业务目标和参考答案；明确条件交给代码；语义条件可交给模型初评；人抽查难例并校准裁判；平台关联版本与结果。不是所有企业都用同一套工具，也不是所有任务都应该由AI判分。

## 本轮是真的测本地项目

使用本机Agent Desk的server/app.mjs、store.mjs、extensions.mjs、providers.mjs等实际模块，包含未提交改动。不是复制一个Prompt绕开应用，也不是评Github旧版。GitHub只用于学习留痕；本地代码无需先上传。

应用创建一个独立实验数据库。8个任务经过真实HTTP接口、FTS检索、上下文拼接、DeepSeek、SSE与消息持久化。正常9次生成请求，其中同会话任务有两轮；AI裁判请求0次。应用源码没有改动。

## 不是凭回答猜原因

ad02资料：灯塔项目使用 pnpm 安装依赖。

问题：这个工作区的第三方包该用哪个工具装？只根据资料回答。

实际证据：

1. 资料已通过应用接口创建并建立索引。
2. 应用没有召回该知识文档，只附上与发布代号有关的手工记忆。
3. 真实模型请求messages同样没有pnpm资料，不是仅网页没有显示。
4. 回答说明缺少安装工具资料，未能完成用户任务。
5. 回答又把手工记忆ID写成了不存在的知识库引用，被独立引用ID检查发现。

这是两个问题：检索没有识别“第三方包”与“依赖”的对应关系；模型又给非知识库资料编造了知识库引用。只修改回答Prompt不能自动把漏检资料送入模型；只修检索也不等于所有引用问题都解决。

Agent Desk当前使用中文双字词与SQLite FTS5/BM25进行词项检索，未使用向量嵌入。换句话说，字词重合帮助找资料，但不同说法可能完全不命中。向量、混合检索或查询改写是候选方向，需要实验验证，不能先宣布加上就更好。

## 三种判断怎么分

- 端口应为46321：可以代码检查，仍须结合资料确保没有其他矛盾。
- 引用ID是否真的来自检索结果：可以代码严格检查。
- 讲得是否清楚、有没有遗漏重要限定、资料能否支持每句话：需要人工或经过校准的模型裁判。

规则通过7/8，只描述这8题和这些检查；不是Agent Desk有87.5%的综合正确率。人工复核仍未完成。案例、请求、答案和失败检查见[首轮报告](../../reports/agentdesk-first-baseline.md)。
